01 · 공유 에셋을 순환으로 오인하지 않는가

A→B→D와 A→C→D에서 D가 각각 나타나고, 두 행 모두 IsCircular=false였습니다. 실제 순환 E→F→E에서는 마지막 E만 true이며 그 뒤 탐색이 없었습니다. Max Depth=3, 순환 노드는 Depth=2이므로 단순 깊이 제한에 의해 종료된 결과와 구분됩니다.

02 · Enter·클릭·Escape·빈 입력을 구분하는가

실제 Enter에서 OnEnter(1) → OnCleared(3)가 연속 발생했습니다. 현재 콜백은 두 번째 이벤트를 무시하여 BranchB를 유지했습니다. 클릭 확정은 BranchC로 갱신했고, C 확정 후 B를 입력하다 Escape를 누르면 C로 돌아갔습니다. 빈 문자열을 Enter로 확정하면 필터가 해제됐습니다.

03 · CSV가 실제 분석 결과의 모드를 유지하는가

B의 Dependencies 결과는 B→D, Referencers 결과는 B→A입니다. 분석 없이 버튼만 바꾸었을 때는 CSV 전체 행이 기존 파일과 동일했습니다. Referencers로 재분석한 뒤에만 트리와 CSV가 함께 바뀌었고, 반대 방향의 버튼 전환에서도 일관성이 유지됐습니다.

이 근거로 말할 수 있는 범위

  • 원본 소스 기준은 724eaba9790859066d7b34baf48c5efd7a9f877e입니다. 원본 플러그인 소스 12개 파일의 실행 전후 SHA-256이 같음을 확인했습니다.
  • 별도 QA 복사본에 추적 로그, 탭 열기 명령, 이전 로직 비교 플래그를 추가하고 실제 빌드했습니다. 현재 코드 검증에서는 이전 로직 플래그를 사용하지 않았습니다. 수정 내역은 instrumentation.diff에 모두 공개했습니다.
  • 테스트 관계는 자동 생성한 QAReferenceAsset(Data Asset)의 저장된 hard reference입니다. Asset Registry에서 관계를 먼저 검증했습니다. 기존에 예시로 든 Blueprint 에셋 자체를 검사한 결과로 표현하면 안 됩니다.
  • 이전 필터는 개발 대화에 보존된 사용자 코드, 이전 CSV는 70c2258 수정 diff를 근거로 해당 처리만 재구성했습니다. 과거 전체 빌드를 실행한 결과가 아닙니다.
  • 이번 결과는 이 세 시나리오의 현재 환경 검증입니다. 대규모 프로젝트 성능, 다른 엔진 버전, 모든 에셋 유형을 검증했다는 의미는 아닙니다.
  • 이번 검증·촬영은 Codex가 자동 수행했습니다. 개발 당시 본인의 구현·검증 기여를 새로 증명하는 기록으로 소급하지 않습니다.

수동으로 꼭 해야 하는 부분

이번 세 사례의 실행·녹화·근거 수집에는 없습니다. 테스트 에셋 생성, 빌드, 에디터 조작, 녹화, CSV/로그 판정까지 완료했습니다. 직접 다시 조작해야만 검증이 성립하는 구조가 아닙니다.
